# Отчет о приложении Memes DB

## Доменная область

Memes DB предназначено для публикации и поиска мемов: изображений, анимаций,
видео и аудио. Пользователь создает аккаунт, загружает файл, просматривает
публикации и удаляет свои медиа. Повторная загрузка файла с тем же SHA-256
отклоняется со ссылкой на существующую публикацию.

Разные разрешения и обрезки одного мема можно объединить в группу вариаций.
Пользователи голосуют за изменение состава групп. Превью, распознанный текст
и признаки для поиска добавляются после публикации отдельным процессом обработки.

## Стек и устройство приложения

| Часть приложения | Технологии |
| --- | --- |
| Frontend | TypeScript, React, Vite; Node.js для раздачи собранного интерфейса |
| Backend | Python 3.12 в контейнерах, FastAPI, Uvicorn, Pydantic |
| Обмен данными | HTTP/REST, JSON; браузер обращается к API |
| Основная СУБД | PostgreSQL 17, SQLAlchemy, asyncpg, Alembic |
| Поиск | PostgreSQL FTS, pg_trgm и pgvector |
| Файлы медиа | S3-совместимое хранилище SeaweedFS |
| Дополнительная обработка | FFmpeg, Pillow; Jina, faster-whisper и PaddleOCR |
| Зависимости и запуск | Poetry, npm, Docker Compose |
| Проверки | pytest, Ruff, mypy, компилятор TypeScript |

Backend состоит из четырех сервисов: Identity управляет аккаунтами,
Catalog публикациями и вариациями, Processing заданиями обработки,
Search поиском. У каждого сервиса своя база и роль в общем экземпляре PostgreSQL.
Сервисы взаимодействуют через REST. Записи outbox/inbox в PostgreSQL обеспечивают
повторяемую доставку событий без отдельного брокера сообщений.

Код разделен на Domain, Application, Infrastructure и Presentation.
Домен содержит бизнес-правила, Application сценарии и интерфейсы,
Infrastructure адаптеры PostgreSQL, S3 и REST, Presentation HTTP-маршруты и CLI.

Пользователи, публикации, группы, голоса, задания и поисковые данные хранятся
в PostgreSQL. В S3 находятся бинарные файлы, а их метаданные и связи в PostgreSQL.
SQLite используется только как удаляемый кэш дополнительного воркера.

## Основные сущности

| Сущность | Назначение |
| --- | --- |
| User | Аккаунт: идентификатор, логин, роли и состояние доступа |
| Media | Публикация: автор, оригинальный файл, хэш, тип и состояние медиа |
| VariationGroup | Группа вариантов одного мема |
| GroupMembership | Принадлежность медиа группе и версия этого членства |
| VariationBallot | Предложение изменить группу и необходимое число голосов |
| VariationVote | Голос пользователя по предложению |
| VariationDecision | Зафиксированное решение об изменении группы |
| FeatureExtraction | Этап получения признака медиа, его версия, состояние и результат |

Сессии авторизации, токены и транспортные DTO не являются сущностями
бизнес-домена. Они относятся к обеспечению прикладных сценариев.

## CRUD

Полный CRUD реализован для аккаунта пользователя:

| Операция | REST API | Результат |
| --- | --- | --- |
| Create | POST /v1/auth/register | Создание аккаунта, HTTP 201 |
| Read | GET /v1/auth/me | Чтение своего аккаунта, HTTP 200 |
| Update | PATCH /v1/auth/login | Изменение логина, HTTP 200 |
| Update | PATCH /v1/auth/password | Изменение пароля, HTTP 204 |
| Delete | DELETE /v1/auth/account | Удаление аккаунта, HTTP 204 |

Изменение и удаление требуют авторизации и подтверждения текущего пароля.
После удаления аккаунта доступ отзывается. Пользователь может сохранить свои
публикации с обезличенным автором либо запросить удаление медиа.

Для публикаций доступны создание через загрузку, чтение ленты и отдельных
медиа, удаление своих медиа и изменение группы вариаций. Оригинал файла
неизменяем: замена содержимого считается новой публикацией.

Frontend содержит регистрацию, вход, загрузку, ленту, поиск, просмотр вариаций
и удаление медиа. Форм изменения и удаления аккаунта в интерфейсе пока нет.
Эти операции доступны через REST API и страницу OpenAPI.

## Соответствие 12 факторам

### 1. Кодовая база

Приложение находится в одном Git-репозитории. Сервисы и frontend собираются
из одного снимка исходников. Разные окружения используют релизы этой кодовой базы.

### 2. Зависимости

Python-зависимости объявлены в pyproject.toml и зафиксированы poetry.lock.
Frontend использует package.json и package-lock.json, сборка выполняет npm ci.
Python работает в изолированном окружении образа. Системные зависимости явно
устанавливаются в Dockerfile. ML-пакеты выделены в дополнительные группы воркера.

### 3. Конфигурация

DSN, адреса сервисов и S3, секреты, CORS/CSRF, порты и ограничения передаются
через окружение. Compose получает значения из локального .env, который не входит
в архив. Генератор создает новые секреты для каждого окружения. Публичные адреса
frontend передаются через /config.js при запуске сервера, без пересборки JavaScript.

### 4. Подключаемые ресурсы

PostgreSQL и S3 подключаются по адресам из окружения. Адаптеры доступа отделены
от бизнес-логики. Можно использовать внешний PostgreSQL с нужными расширениями
и другое совместимое S3-хранилище, изменив настройки подключения.
Соседние REST-сервисы также подключаются через конфигурацию.

### 5. Сборка, релиз и запуск

Build устанавливает зависимости и собирает образы и frontend. Release связывает
готовые образы с окружением и запускает миграции. Run запускает процессы без
установки пакетов, изменения схемы БД или скачивания моделей.

### 6. Процессы

Важное состояние хранится в PostgreSQL и S3. API и фоновые процессы можно
перезапускать без потери опубликованных данных. Временные файлы и кэш воркера
не являются единственной копией результатов.

### 7. Привязка портов

API самостоятельно обслуживают HTTP через Uvicorn, frontend через Node.js.
Порты задаются окружением и публикуются Compose. Для базового запуска внешний
веб-сервер не требуется. Воркер получает задания исходящими REST-запросами.

### 8. Параллелизм

Web API, outbox, coordinator, maintenance и worker являются отдельными
типами процессов. Можно добавлять экземпляры фоновых процессов и воркеров.
Блокировки PostgreSQL, lease и идентификаторы попыток согласуют работу
и не позволяют принять устаревший результат.

В Compose запускается по одному экземпляру API с фиксированным портом.
Для нескольких экземпляров API потребуется балансировщик и настройка публикации
портов. Бизнес-состояние не привязано к конкретному экземпляру процесса.

### 9. Утилизируемость

Процессы обрабатывают SIGTERM и имеют ограниченное время завершения.
HTTP-запросы используют таймауты. Незавершенные задания доступны повторно
после истечения lease. Миграции и скачивание моделей вынесены из запуска
рабочих процессов. Compose задает время корректного завершения контейнеров.

### 10. Паритет разработки и эксплуатации

Локальный запуск использует PostgreSQL, S3, контейнеры и те же миграции,
которые нужны в других окружениях.
Окружения отличаются адресами, секретами, HTTPS и количеством процессов.
Отдельное production-развертывание в рамках задания не выполнялось.

### 11. Логирование

Backend пишет структурированные события в stdout, frontend в stdout/stderr.
Приложение не создает собственные файлы логов. Их сбор и ротацию выполняет Docker.
События backend содержат идентификатор релиза и запроса; пароли и токены
не являются полями прикладных логов.

### 12. Административные задачи

Миграции Alembic, создание оператора, регистрация воркера и подготовка моделей
выполняются отдельными CLI-процессами. Они используют образ и окружение
соответствующего сервиса. API не выполняет создание таблиц при запуске.
В Compose миграции завершаются до запуска зависимых API.

## Запуск для проверки задания

Для регистрации, CRUD аккаунта, загрузки, ленты и удаления медиа достаточно CPU.
ML-воркер, GPU и веса моделей для этих операций не нужны. Без воркера
распознавание и семантический поиск недоступны.

Нужны Docker с Compose v2 и Python 3.11 или новее. Из корня распакованного проекта:

```sh
python deploy/scripts/generate_env.py --release-id submission-v1 --public-host localhost
docker compose --env-file deploy/.env -f deploy/compose.yaml build identity frontend
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
docker compose --env-file deploy/.env -f deploy/compose.yaml ps -a
```

Генератор предназначен для нового окружения и не перезаписывает существующий .env.
Дождитесь состояния healthy у API и frontend. Exited (0) у миграционных
и инициализирующих контейнеров означает успешное завершение.

Frontend: http://localhost:5173. OpenAPI Identity: http://localhost:8080/docs.
Catalog, Processing и Search предоставляют /docs на портах 8081, 8082 и 8083.
PostgreSQL и S3 сохраняют данные в Docker volumes.
