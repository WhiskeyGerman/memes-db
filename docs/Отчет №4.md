# ДЗ 4. Метрики приложения в Kubernetes

Развернул VictoriaMetrics и vmagent в том же minikube, где работает приложение.
Подключил метрики Python, четыре бизнес-метрики и postgres-exporter.
[Настройки Helm и манифест настройки роли](../deploy/k8s/monitoring/),
[манифесты API](../deploy/k8s/api.yaml), [PostgreSQL](../deploy/k8s/postgres.yaml).

## Запуск

PostgreSQL, S3, Secrets и Gateway уже настроены в предыдущих ДЗ.
Нужны Docker, minikube, kubectl, Helm и Python. Команды выполняются из корня.

Собираем backend с метриками и загружаем образ:

```shell
docker build --file deploy/Dockerfile --target backend --build-arg RELEASE_ID=task-04-v1 --tag memes-db-backend:task-04-v1 .
minikube image load memes-db-backend:task-04-v1
kubectl apply -f deploy/k8s/config.yaml -f deploy/k8s/api.yaml -f deploy/k8s/background.yaml
kubectl -n memes-db rollout status deployment -l app.kubernetes.io/component=api --timeout=180s
```

Secret `postgres-exporter` с ключом `password` описан в
[шаблоне секретов](../deploy/k8s/secrets.example.yaml). Один и тот же пароль
используют Job настройки роли и контейнер postgres-exporter.

Затем настраиваем роль и добавляем контейнер к PostgreSQL:

```shell
kubectl apply -f deploy/k8s/monitoring/postgres-exporter-user.yaml
kubectl -n memes-db wait --for=condition=complete job/postgres-exporter-user --timeout=120s
kubectl apply -f deploy/k8s/postgres.yaml
kubectl -n memes-db rollout status statefulset/postgres --timeout=180s
```

Job создаёт роль `postgres_exporter` и выдаёт ей `pg_monitor` и подключение
к базе `postgres`.

Устанавливаем два официальных Helm-чарта с закреплёнными версиями:

```shell
helm repo add vm https://victoriametrics.github.io/helm-charts
helm repo update vm
helm upgrade --install vm-single vm/victoria-metrics-single --version 0.49.0 --namespace monitoring --create-namespace -f deploy/k8s/monitoring/victoria-metrics-values.yaml
helm upgrade --install vmagent vm/victoria-metrics-agent --version 0.50.0 --namespace monitoring -f deploy/k8s/monitoring/vmagent-values.yaml
kubectl -n monitoring rollout status statefulset/victoria-metrics --timeout=180s
kubectl -n monitoring rollout status deployment/vmagent --timeout=180s
```

Оба компонента используют VictoriaMetrics `v1.154.0`. Хранилище работает
в single-node режиме: PVC 2 ГиБ, срок хранения 7 дней. Grafana не устанавливалась.
Подход основан на [официальном руководстве](https://docs.victoriametrics.com/guides/k8s-monitoring-via-vm-single/).

## Как собираются метрики

Используется Pull-модель. Каждые 15 секунд vmagent запрашивает `/metrics`
у четырёх API и postgres-exporter, затем отправляет данные в VictoriaMetrics
через `/api/v1/write`. Таймаут одного сбора - 10 секунд.

Service discovery обращается к Kubernetes API и ищет Pod в namespace
`memes-db` с меткой приложения. На шаблоны Pod в Deployment API и StatefulSet
PostgreSQL добавлены аннотации:

```yaml
prometheus.io/scrape: "true"
prometheus.io/port: "8080"  # Для postgres-exporter - 9187.
prometheus.io/path: /metrics
```

В конфигурации нет фиксированных IP Pod: после пересоздания новый адрес
обнаруживается автоматически. Фильтр сравнивает порт контейнера с аннотацией,
поэтому у PostgreSQL выбирается только контейнер экспортёра. Порт самой БД
5432 не становится вторым таргетом того же `/metrics`.

В VictoriaMetrics добавляются метки `job`, `namespace`, `pod` и `container`.
`job` содержит имя сервиса: `identity`, `catalog`, `processing`, `search`
или `postgres`. Метрики доступны внутри кластера без авторизации.
В публичных HTTPRoute маршрута к `/metrics` нет; для локальной проверки
используется `port-forward` на loopback.

## Экспортёры

В backend используется уже подключённая библиотека `prometheus-client`.
В отдельный registry каждого API добавлены готовые `GCCollector`,
`PlatformCollector` и `ProcessCollector`. Они экспортируют сборки мусора
Python, версию интерпретатора, CPU, память, время старта и файловые дескрипторы
процесса. Метрики процесса собираются в Linux-контейнерах minikube.

Сохранились HTTP-счётчик `memes_http_requests_total` и гистограмма
`memes_http_request_duration_seconds`. В метках используется шаблон маршрута,
а не URL с идентификаторами.

PostgreSQL наблюдается готовым `prometheus-community/postgres_exporter`
версии `v0.20.1`. Это второй контейнер в `postgres-0`: он подключается
к БД по `127.0.0.1:5432` и отдаёт `/metrics` на порту 9187.
Экспортируются `pg_up`, статистика транзакций, подключений и размеров баз.

## Бизнес-метрики

| Метрика | Сервис | Что измеряет |
| --- | --- | --- |
| `memes_users_active` | Identity | Количество пользователей со статусом `active`. Заблокированные и удаляемые аккаунты исключены. |
| `memes_media_published` | Catalog | Количество уникальных медиа со статусом `published`. Незавершённые загрузки и удалённые публикации исключены. |
| `memes_groups_active` | Catalog | Количество групп со статусом `active`, включая группы из одного мема. Объединённые и пустые группы исключены. |
| `memes_ballots_open` | Catalog | Количество голосований со статусом `open`, которые ещё собирают голоса. Исполненные, устаревшие и достигшие порога исключены. |

Все четыре показателя имеют тип Gauge: это текущее состояние, а не число
событий за всё время. Например, после публикации двух мемов появляются две
группы; после их объединения остаётся одна. Значение может уменьшаться,
поэтому `rate()` для этих метрик не используется.

При каждом сборе сервис выполняет фиксированные read-only SQL-агрегаты
только в своей базе и передаёт значения в Gauge клиентской библиотеки.
Использован существующий механизм снимков, новые таблицы и миграции не нужны.
Перезапуск API не обнуляет бизнес-показатели: они снова читаются из БД.
Логины, идентификаторы пользователей и медиа в метки не попадают.

## Проверка

Подсистема мониторинга и оба контейнера PostgreSQL должны быть готовы:

```shell
kubectl -n monitoring get pods,svc
kubectl -n memes-db get pod postgres-0
```

Каждый `port-forward` запускается в отдельном терминале:

```shell
kubectl -n monitoring port-forward --address 127.0.0.1 service/victoria-metrics 8428:8428
kubectl -n monitoring port-forward --address 127.0.0.1 service/vmagent 8429:8429
```

В третьем терминале проверяем данные, уже сохранённые в VictoriaMetrics:

```shell
curl "http://127.0.0.1:8428/api/v1/query?query=up"
curl "http://127.0.0.1:8428/api/v1/query?query=python_info"
curl "http://127.0.0.1:8428/api/v1/query?query=pg_up"
curl "http://127.0.0.1:8428/api/v1/query?query=memes_users_active"
curl "http://127.0.0.1:8428/api/v1/query?query=memes_media_published"
curl "http://127.0.0.1:8428/api/v1/query?query=memes_groups_active"
curl "http://127.0.0.1:8428/api/v1/query?query=memes_ballots_open"
```

[Таргеты vmagent](http://127.0.0.1:8429/targets) показывают пять успешных
таргетов: четыре API и postgres-exporter. Для них `up=1`, для PostgreSQL
также `pg_up=1`. `up` подтверждает получение метрик по HTTP, а `pg_up` -
успешное подключение самого экспортёра к БД.
